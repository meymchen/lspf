# Migrating from lspf 0.1 to 0.2

This guide ports an lspf 0.1.x server to the 0.2 model locked by ADRs
0017–0020. It is self-contained: you do not need to read the ADRs to
migrate.

Every `// 0.2` block below is compiled as a documentation test against the
implemented surface, so what you read here is what the crate accepts. The
`// 0.1` blocks show the code you are migrating away from and do not compile
under 0.2.

## What 0.2 removes

lspf 0.2 removes the `LanguageServer` trait and its `documents()` getter
outright. There is no long-lived adapter and no deprecation cycle: the old
trait is gone in the 0.2 release, not phased out.

Rationale for removing without an adapter:

- lspf is still 0.x, where breaking changes are sanctioned;
- an adapter would force the framework to run two lifecycle and
  document-ownership models side by side; and
- the current example and downstream surface is small enough to migrate
  directly.

In place of the trait, 0.2 registers typed handlers on a builder:

- `Server::builder(state)` wraps your state in one `Arc<S>` shared by every
  handler for the connection;
- `feature` / `request` / `notification` / `command` register handlers with
  native Rust signatures; and
- `build()` validates the registrations and returns `Result<Server<S>,
  BuildError>`.

## Handler signatures at a glance

- Request handler:
  `Fn(Arc<S>, Context, Params, CancellationToken) -> Future<Output = Result<ResultType, LspError>>`
- Notification handler: `Fn(Arc<S>, Context, Params) -> Future<Output = ()>`

`Context` arrives by value and is cheap to clone. `Arc<S>` is your state,
wrapped by the framework — you never wrap it yourself.

Registrations name their wire type through a marker: `.request::<R, _, _>` and
`.notification::<N, _, _>` take an `lspf::types::request::Request` or
`lspf::types::notification::Notification` marker, and the two inferred
parameters are your handler and its future.

## Struct state

0.1 stored framework state (the `Documents` store) inside your struct and
handed it back through the required `documents()` getter:

```rust,ignore
// 0.1
struct Hello {
    documents: Documents,
}

impl Hello {
    fn new() -> Self {
        Self {
            documents: Documents::new(),
        }
    }
}

impl LanguageServer for Hello {
    fn documents(&self) -> &Documents {
        &self.documents
    }
}
```

In 0.2 the framework owns the documents. Your struct carries only your own
application state, and you pass it to `Server::builder`:

```rust
// 0.2
struct State {
    // Only your own application state lives here — no Documents,
    // no Context, no framework handles.
}

impl State {
    fn new() -> Self {
        Self {}
    }
}

let server = lspf::Server::builder(State::new())
    // ...registrations...
    .build()
    .expect("the static registrations are valid");
```

Every handler receives that state as `Arc<State>`. Handlers reach the
documents through the `Context` parameter: `ctx.documents()` returns a
minimal read-only view (`DocumentsView`) with document lookup and position
conversion and no mutation operation; user code never constructs `Documents`
or `Context` itself.

## Lifecycle handlers

0.1 overrode trait methods, and could shape capabilities by overriding
`server_capabilities()`:

```rust,ignore
// 0.1
impl LanguageServer for Hello {
    async fn initialize(
        &self,
        _ctx: &Context,
        _params: InitializeParams,
        _ct: CancellationToken,
    ) -> Result<InitializeResult, LspError> {
        Ok(InitializeResult {
            capabilities: self.server_capabilities(&_params),
            server_info: Some(ServerInfo {
                name: "hello".into(),
                version: None,
            }),
        })
    }

    async fn shutdown(
        &self,
        _ctx: &Context,
        _ct: CancellationToken,
    ) -> Result<(), LspError> {
        Ok(())
    }

    async fn exit(&self, _ctx: &Context) {}
}
```

0.2 moves the initialize override to a dedicated builder hook.
`ServerCapabilities` are generated by the framework from your registrations —
the hook cannot replace them, and `server_capabilities()` no longer exists:

```rust
// 0.2
# struct State;
# impl State { fn new() -> Self { Self } }
use std::sync::Arc;

use lspf::types::{InitializeParams, ServerInfo};
use lspf::{CancellationToken, Context, LspError, Server};

// Request-handler shape; runs after the Workspace is established and
// before capabilities are returned. Its optional ServerInfo is combined
// with the framework-generated capabilities.
async fn on_initialize(
    _state: Arc<State>,
    _ctx: Context,
    _params: InitializeParams,
    _ct: CancellationToken,
) -> Result<Option<ServerInfo>, LspError> {
    Ok(Some(ServerInfo {
        name: "hello".into(),
        version: None,
    }))
}

let server = Server::builder(State::new())
    .on_initialize(on_initialize)
    .build()
    .expect("the static registrations are valid");
```

Related moves:

- `shutdown` and `exit` are protocol built-ins in 0.2: the engine answers
  `shutdown`, cancels the outstanding work, and derives the exit code from
  lifecycle state. ADR 0018 specifies `on_shutdown` and `on_exit` hooks that
  observe those built-ins, but they are not on the builder yet — a 0.1
  override that only returned `Ok(())` has nothing left to port. An override
  that did real teardown has one place to go meanwhile: serving now *returns*
  its `Outcome` (see [stdio serve](#stdio-serve)), so the work moves after the
  `.serve(...).await` in `main`, where it runs once the connection has closed
  and every handler task has been joined.
- The 0.1 `initialized` notification override registers as
  `.notification::<lspf::types::notification::Initialized, _, _>(handler)`.
- Initialization-dependent route or capability registration does not go in
  `on_initialize`; it goes in the single synchronous
  `.configure_initialize(|params, registrar| Ok(()))` transaction, which
  runs before the Router is frozen and capabilities are computed.

## The didOpen hook (and other document notifications)

0.1 overrode the trait method. The framework updated its documents
around your override:

```rust,ignore
// 0.1
impl LanguageServer for Hello {
    async fn text_document_did_open(
        &self,
        ctx: &Context,
        params: DidOpenTextDocumentParams,
    ) {
        // Framework state was already updated; react here.
    }
}
```

0.2 registers a post-mutation hook for the built-in notification through
the ordinary `notification` registration. Registering a built-in
notification name records the hook instead of a Router entry:

```rust
// 0.2
# struct State;
# impl State { fn new() -> Self { Self } }
use std::sync::Arc;

use lspf::types::DidOpenTextDocumentParams;
use lspf::types::notification::DidOpenTextDocument;
use lspf::{Context, Server};

async fn on_did_open(
    _state: Arc<State>,
    ctx: Context,
    params: DidOpenTextDocumentParams,
) {
    // Runs after the built-in mutation: ctx.documents() already contains
    // the opened document.
    let opened = ctx.documents().get(&params.text_document.uri);
    assert!(opened.is_some());
}

let server = Server::builder(State::new())
    .notification::<DidOpenTextDocument, _, _>(on_did_open)
    .build()
    .expect("the static registrations are valid");
```

For every built-in notification the ordering is fixed:

1. decode typed parameters;
2. perform built-in validation and mutation;
3. invoke the user hook.

The hook observes post-mutation state and cannot suppress, roll back, or
reorder the built-in. A decode or validation failure means the hook never
runs. Registering two hooks for the same built-in notification is a
`BuildError`. The other 0.1 document overrides map as follows:

- `text_document_did_change` and `text_document_did_close` are also built-in
  mutations; each becomes one `.notification::<N, _, _>(handler)`
  post-mutation hook with the same ordering guarantees as didOpen.
- `text_document_did_save` has no built-in mutation behind it, so
  `.notification::<lspf::types::notification::DidSaveTextDocument, _, _>(handler)`
  registers an ordinary Router notification handler rather than a
  post-mutation hook.

Because document sync is a built-in rather than a registration, the engine
advertises `textDocumentSync` itself: a server that registers no hook at all
still tracks documents, and 0.1's `TEXT_DOCUMENT_SYNC` associated const has
nothing to replace it.

## Diagnostics

0.1 pushed diagnostics through a helper on the borrowed `&Context`:

```rust,ignore
// 0.1
async fn text_document_did_open(
    &self,
    ctx: &Context,
    params: DidOpenTextDocumentParams,
) {
    ctx.publish_diagnostics(PublishDiagnosticsParams {
        uri: params.text_document.uri,
        version: Some(params.text_document.version),
        diagnostics: vec![/* ... */],
    });
}
```

In 0.2, outgoing traffic goes through the typed `Client` handle exposed by
`Context`. `Client::notify` is synchronous: it encodes the parameters,
enqueues them on the engine-owned outbound queue without allocating a request
ID, and returns — there is nothing to await, and the only failure is a
closing connection:

```rust
// 0.2
# struct State;
use std::sync::Arc;

use lspf::types::notification::PublishDiagnostics;
use lspf::types::{DidOpenTextDocumentParams, PublishDiagnosticsParams};
use lspf::Context;

async fn on_did_open(
    _state: Arc<State>,
    ctx: Context,
    params: DidOpenTextDocumentParams,
) {
    let result = ctx
        .client()
        .notify::<PublishDiagnostics>(PublishDiagnosticsParams {
            uri: params.text_document.uri,
            version: Some(params.text_document.version),
            diagnostics: vec![/* ... */],
        });
    if let Err(error) = result {
        tracing::warn!(%error, "publish diagnostics failed");
    }
}
```

`Client` is also the handle for typed server-to-client requests
(`Client::request`), which reserve an engine-owned ID and — unlike `notify` —
await the correlated response.

## stdio serve

0.1 constructed the server value inline, served it over stdio, and let the
entry point terminate the process:

```rust,ignore
// 0.1
#[tokio::main]
async fn main() -> lspf::Result<()> {
    tracing_subscriber::fmt()
        .with_writer(std::io::stderr)
        .with_env_filter(tracing_subscriber::EnvFilter::from_default_env())
        .init();
    lspf::stdio(Hello::new()).serve().await
}
```

0.2 keeps the `lspf::stdio(server).serve()` call shape, but the argument is
now a built `Server`, and serving returns the `Outcome` that ended the
connection instead of exiting. Mapping that outcome onto a process
disposition is the binary's decision:

```rust,no_run
// 0.2
# struct State;
# impl State { fn new() -> Self { Self } }
# async fn on_did_open(
#     _state: std::sync::Arc<State>,
#     _ctx: lspf::Context,
#     _params: lspf::types::DidOpenTextDocumentParams,
# ) {}
#[tokio::main]
async fn main() -> lspf::Result<()> {
    tracing_subscriber::fmt()
        .with_writer(std::io::stderr)
        .with_env_filter(tracing_subscriber::EnvFilter::from_default_env())
        .init();

    let server = lspf::Server::builder(State::new())
        .notification::<lspf::types::notification::DidOpenTextDocument, _, _>(on_did_open)
        .build()
        .expect("the static registrations are valid");
    let outcome = lspf::stdio(server).serve().await?;
    std::process::exit(outcome.code());
}
```

`Outcome::code()` is the LSP exit code: 0 only after a successful `shutdown`
followed by `exit`, and 1 for every other ending (`exit` without `shutdown`,
peer disconnect, writer failure, failed initialize transaction).

The custom-transport escape hatch is `Server::serve`, taking any `Transport`
implementation and returning the same `Outcome`:

```rust
// 0.2
# struct State;
# fn example<T: lspf::Transport>(transport: T) {
# let _ = async move {
let server = lspf::Server::builder(State)
    .build()
    .expect("the static registrations are valid");
let outcome = server.serve(transport).await?;
println!("connection ended: {outcome:?}");
# Ok::<(), lspf::Error>(())
# };
# }
```

One `Server` owns exactly one connection; a second connection requires a
second `Server`. Because serving returns rather than exits, an in-process
test can drive a connection over an in-memory transport and assert on the
`Outcome` without taking the test runner down.

## Concurrency limit

0.1 configured the in-flight handler cap at the serve entry point or on the
stdio builder, with `DEFAULT_CONCURRENCY_LIMIT` (64) as the implicit value:

```rust,ignore
// 0.1
lspf::serve(server, transport).await?; // uses DEFAULT_CONCURRENCY_LIMIT (64)
lspf::serve_with_limit(server, transport, 128).await?;
lspf::stdio(server).concurrency_limit(128).serve().await?;
```

In 0.2 the cap is part of the fixed, framework-owned default stack —
`PanicIsolation → Tracing → ConcurrencyLimit → user layers → RouterService`
— and is configured on the `ServerBuilder`, not on the transport or serve
call:

```rust
// 0.2
# struct State;
# impl State { fn new() -> Self { Self } }
let server = lspf::Server::builder(State::new())
    .concurrency_limit(128)
    .build()
    .expect("a non-zero limit is valid");
```

Notes on the 0.2 semantics:

- Omitting `concurrency_limit` keeps the framework default cap.
- A limit of `0` fails validation with `BuildError::InvalidConcurrencyLimit`.
- Transport builders no longer carry the knob: business policy moves to the
  `ServerBuilder`.
- The permit is acquired before any user layer runs and is held until the
  call's result completes; tracing spans include the wait for a permit.
- There is no opt-out switch: the 0.1-era `.no_default_layers()` idea is
  gone, and `ConcurrencyLimit` cannot be removed or reordered.

## lspf-hello coverage

The `lspf-hello` example (0.1) uses the following surface; each row points
at its mapping above.

| 0.1 usage in `lspf-hello` | 0.2 mapping |
| --- | --- |
| `impl LanguageServer for Hello` | Removed trait; registrations move to `Server::builder` (all sections) |
| `struct Hello { documents: Documents }` + `Documents::new()` | Framework-owned store; user struct holds only app state (Struct state) |
| `fn documents(&self) -> &Documents` | Removed getter; handlers use `ctx.documents()` (Struct state) |
| `text_document_did_open` override | `.notification::<DidOpenTextDocument, _, _>(handler)` post-mutation hook (The didOpen hook) |
| `ctx.publish_diagnostics(params)` | `ctx.client().notify::<PublishDiagnostics>(params)`, synchronous (Diagnostics) |
| `lspf::stdio(Hello::new()).serve().await` | `lspf::stdio(server).serve().await` with a built `Server`, returning an `Outcome` (stdio serve) |
| `lspf::Result` return from `main` | Unchanged, but `serve()` now resolves to `lspf::Result<Outcome>` (stdio serve) |
| `lspf::types::{...}` imports | Unchanged; `lspf::types` still re-exports `lsp-types` |
| `#[tokio::main]` + `tracing_subscriber` init | Unchanged; not lspf API |

## Full 0.2 lspf-hello

The complete 0.2 shape of the example, mirroring
[`crates/lspf-hello/src/main.rs`](../../crates/lspf-hello/src/main.rs):

```rust,no_run
use std::sync::Arc;

use lspf::types::notification::{DidOpenTextDocument, PublishDiagnostics};
use lspf::types::{
    Diagnostic, DiagnosticSeverity, DidOpenTextDocumentParams, Position,
    PublishDiagnosticsParams, Range,
};
use lspf::{Context, Server};

struct State;

impl State {
    fn new() -> Self {
        Self
    }
}

async fn on_did_open(_state: Arc<State>, ctx: Context, params: DidOpenTextDocumentParams) {
    let uri = params.text_document.uri;
    // The built-in mutation has already run, so the opened document — and the
    // version every later handler will see — is in the store.
    let Some(document) = ctx.documents().get(&uri) else {
        return;
    };
    let result = ctx
        .client()
        .notify::<PublishDiagnostics>(PublishDiagnosticsParams {
            uri,
            version: Some(document.version()),
            diagnostics: vec![Diagnostic {
                range: Range {
                    start: Position {
                        line: 0,
                        character: 0,
                    },
                    end: Position {
                        line: 0,
                        character: 0,
                    },
                },
                severity: Some(DiagnosticSeverity::INFORMATION),
                source: Some("lspf-hello".into()),
                message: "lspf saw this document open".into(),
                ..Diagnostic::default()
            }],
        });
    if let Err(error) = result {
        tracing::warn!(%error, "publishing the open diagnostic failed");
    }
}

#[tokio::main]
async fn main() -> lspf::Result<()> {
    tracing_subscriber::fmt()
        .with_writer(std::io::stderr)
        .with_env_filter(tracing_subscriber::EnvFilter::from_default_env())
        .init();

    let server = Server::builder(State::new())
        .notification::<DidOpenTextDocument, _, _>(on_did_open)
        .build()
        .expect("the static registrations are valid");
    let outcome = lspf::stdio(server).serve().await?;
    std::process::exit(outcome.code());
}
```
